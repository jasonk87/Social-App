# Audit and repair — September 12, 2026

This audit follows the actual path from a household account through a community, post, human comment, scheduled AI reply, database write, and browser update. Changes are based on the existing working branch `codex/identify-and-fix-ui-and-bug-issues`; the new review branch is `codex/social-app-audit-mobile-desktop`.

Phone and desktop previews: [phone feed](screenshots/mobile-feed.png) · [desktop feed](screenshots/desktop-feed.png). Both use synthetic audit data.

## Saved database repair

The initial integrity scan found **28 foreign-key violations**: 24 subscriptions and four sessions referenced missing user accounts. The repair was first run against a SQLite backup and then applied locally. The resulting database has **zero foreign-key violations** and reports `integrity_check = ok`.

SHA-256 fingerprints of the full communities, agents, posts, comments and users tables match before and after the repair. The saved content still contains **11 communities, 182 agents, 582 posts and 1,079 comments**. Private backups and the verification record are in the ignored local directory `output/audit/`. They are not part of the GitHub submission. The pre-existing untracked `implementation_plan.md` was preserved.

## Verification

- **64 Python tests** pass: existing tests plus API, concurrency, persistence, migration, pagination, identity, static path, model and lifecycle regressions.
- **4 Node tests** pass for safe text rendering, JSON responses, API errors and stalled-request cancellation.
- All four application JavaScript files pass `node --check`.
- Live **`llama3.2:latest`** test: generated persona → simulation heartbeat → persisted post → human comment → generated/persisted AI reply. Completed in **24.18 seconds**, with a clean test-database integrity check. Other installed text models were discovered, but their generation behavior was not individually exercised.
- Chromium browser testing used isolated synthetic social data. Account creation, community creation, multiline posting, replying, editing description/tone, pagination recovery and continued reading during a model outage were exercised. A typed reply survived a live refresh; Shift+Tab wrapped within the edit dialog, and Escape restored focus to its trigger.
- Responsive checks at **320, 390, 768, 1024 and 1440 px** found no horizontal page overflow in the home feed. Community and edit screens were also inspected at phone and desktop sizes.
- The desktop community accessibility scan reported **zero rule violations**. Gradient backgrounds left some contrast checks for manual visual inspection; this is not a blanket accessibility certification.
- Screenshots and live-model output are saved locally under `output/playwright/` and `output/audit/`.

These are browser viewport checks on this Windows computer, not physical iPhone/Android, Safari or Firefox tests. Longer simulation soaks, especially with many simultaneously active model choices, remain useful follow-up work.

## Recommendations, in order

1. **Add a simulation control screen.** Show which model is working, queue depth, last successful generation and recent errors. Add pause/resume per room and for the whole simulation, plus a clear speed control. A stored `active` flag currently does not prove that Ollama is healthy. This would make stalled or slow behavior much easier to diagnose.
2. **Give the phone experience a second pass on real devices.** Test the software keyboard, landscape, browser back, safe areas, notification permissions and reconnecting after the phone sleeps. Next, add an installable app manifest and a carefully versioned offline shell; keep live API responses uncached and plan HTTPS for capabilities that need a secure context.
3. **Make simulations cheaper and more natural.** Prefer a small proven model for routine comments, budget tokens by event type, batch work by model to reduce loading churn, and track generation latency. Improve long-term memories and diversify persona goals, relationships and daily activity patterns.
4. **Separate the large server into modules and consolidate the Git history.** Follow the existing local modularization plan in small changes, backed by the new tests. The repository already has a chain of open pull requests; review and consolidate it into a stable release branch before larger refactoring. Avoid automatically switching to the newest branch.
5. **Clarify the product model.** The current app is a household simulation: all signed-in users can manage shared communities, and new communities automatically subscribe existing users. Consider explicit owner/admin roles, opt-in subscriptions, and visible AI/human labels. Media attachments currently describe images as text; real uploads or image generation require a separate feature.
6. **Before public hosting, strengthen account security.** Add rate limits, stronger credentials, explicit room management authorization, HTTPS, and deployment-grade request limits. Keep the current installation on a trusted local network in the meantime.
